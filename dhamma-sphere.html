Dhamma Sphere

A Buddhist learning and community platform: a doctrine library with AI translation, a social feed with threaded discussions, and a book marketplace where authors and publishers sell to readers. I designed and built it end to end — the database, the REST API and the Vue frontend.

Overview

ConceptX is professional work whose code I can't share. Dhamma Sphere is the project where you can read every line: a Vue 3 single-page app talking to a versioned Laravel REST API, secured with Laravel Passport bearer tokens and backed by a MySQL schema I designed around three areas — the doctrine library, the community feed and the marketplace.

Readers browse and discuss teachings; authors and publishers also get a shop where they list books, manage stock and see their sales.

Features

What the application does today.

Authentication

Register, login, logout and "me" endpoints using Passport access tokens. The Vue router blocks guest-only and protected pages.

User roles

Three roles — user, author and publisher. A custom role: middleware protects the seller-only API routes.

Doctrine library

A paginated library of teachings with keyword search across title, topic and content.

AI translation & suggestions

OpenAI-powered translation of teachings. When a search finds nothing, the AI suggests related teachings.

Posts & sharing

A community feed. Posts can link to a teaching and track share counts.

Nested comments

Replies to comments through a self-referencing parent_id, shown as a thread under each comment.

Likes

One like per user per post, enforced by the database, with a stored counter for fast feeds.

Book shop

Authors and publishers create a shop profile, list books and manage stock.

Cart

A Pinia store saved to localStorage, so the cart survives page reloads.

Checkout & orders

A transactional checkout that locks stock rows, so the same copy can't be sold twice.

Payments

Payment methods are stored as data, and every order gets a payment record. The gateway is simulated for now; cash on delivery leaves the order unpaid.

Seller analytics

Revenue, units sold and orders for each shop.

Database Design

The schema I designed, taken from the project's migrations. Each arrow runs from a foreign key to the table it references. Passport's oauth_* tables are left out.

Engineering Decisions

The problems that shaped the design and how I solved each one.

1 · Preventing overselling at checkout

Problem
Books have limited stock. If two buyers check out the last copy at the same moment, both requests could read "1 in stock" and both succeed.
Approach
Treat checkout as a single unit of work. Checking stock, decrementing it, and creating the order, its items and the payment record either all succeed or all roll back.
Implementation
OrderService::checkout runs inside DB::transaction() and loads the ordered books with lockForUpdate(), so a second checkout waits for the first to commit. If stock is short, a validation error is thrown and the whole transaction rolls back.
Result
Stock can't go negative, and a failed checkout leaves no half-created orders.
return DB::transaction(function () use ($user, $data) {
    $books = Book::whereIn('id', collect($data['items'])->pluck('id'))
        ->lockForUpdate()          // concurrent checkouts wait here
        ->get()->keyBy('id');

    foreach ($data['items'] as $item) {
        $book = $books->get($item['id']);
        if (! $book || $book->stock < $item['quantity']) {
            throw ValidationException::withMessages([...]);  // rolls everything back
        }
        $book->decrement('stock', $item['quantity']);
    }
    // create order, order items (title/price snapshot) and payment record
});

2 · Keeping order history accurate

Problem
Sellers can change prices or delete books after a sale. If orders only pointed at the live catalogue, past orders would silently change or break.
Approach
Record what was bought at the moment of purchase instead of relying on a reference alone.
Implementation
order_items copies the title and price at checkout. book_id is nullable with ON DELETE SET NULL, and the order stores the customer's name, email and shipping address.
Result
Past orders stay correct when the catalogue changes or a book is removed.

3 · One like per user, cheap to display

Problem
Likes must never double-count, and the feed shouldn't count rows for every post on every page load.
Implementation
A post_likes table with a unique(post_id, user_id) constraint. PostService::like toggles the like and updates the stored likes_count in the same transaction.
Result
The database itself rejects duplicate likes, and the feed reads a stored counter instead of counting rows.

4 · A predictable API contract

Problem
Without conventions, each endpoint returns data and errors in a slightly different shape, and the frontend fills up with special cases.
Implementation
Routes are versioned under /api/v1. Every Form Request extends a BaseRequest that returns validation errors as one 422 JSON structure. A ResponseHelper trait wraps every response in {status, message, code, data}, and API Resources control exactly which fields leave the server.
Result
The Vue app can rely on one response shape for every endpoint, and changing a model doesn't accidentally change or leak fields in the API.
